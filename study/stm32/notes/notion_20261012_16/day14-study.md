# 학습 정리 · 포인터, 드라이버 분리, 버튼 디버깅

## 1. 값 복사와 주소 전달
<image src="file-upload://3fb6cbe6-8e4d-81b3-8912-00b2e464d4bc"></image>
```c
int count = 10;
int saved = count;
int *p = &count;
*p = 20;
```
마지막에는 count=20, saved=10이다. saved에는 당시의 값 10을 복사했다. p에는 count의 주소를 저장했고, *p는 그 주소에 있는 원본 공간에 접근한다. *p라는 별도 변수가 생기는 것은 아니다.
선언의 int *p는 “p를 포인터로 만든다”는 뜻이고, 선언 후 *p = 20은 “가리키는 곳에 20을 쓴다”는 뜻이다. p = &count는 p에 주소를 저장하는 동작이다.
```c
void reset(int *value)
{
    *value = 0;
}
/* 다른 함수 안에서 사용 */
reset(&count);
```
함수의 매개변수 value에도 주소의 복사본이 전달된다. 복사한 주소가 같은 원본을 가리키므로 원본 count를 수정할 수 있다. 함수 반환 뒤 매개변수의 수명은 끝나지만 원본에 쓴 값은 남는다.
현재 STM32 32비트 환경에서 일반 데이터 포인터의 크기는 4바이트다. 모든 컴퓨터에서 주소 크기가 4바이트인 것은 아니다. int *p와 char *p의 차이는 가리키는 자료형이며, p+1의 이동 단위도 해당 자료형 크기에 따라 달라진다.
## 2. 배열과 구조체가 필요한 이유
배열은 같은 자료형의 원소를 연속으로 묶는다. 구조체는 서로 관련된 여러 정보를 하나의 대상으로 묶는다. GPIO 포트와 핀은 함께 있어야 LED 하나를 정확히 지정할 수 있다.
```c
typedef struct {
    GPIO_TypeDef *port;
    uint16_t pin;
} led_t;

void led_on(const led_t *led)
{
    HAL_GPIO_WritePin(led->port, led->pin, GPIO_PIN_SET);
}
```
typedef는 자료형에 이름을 붙인다. led->pin은 (*led).pin과 같은 뜻이다. const led_t *는 이 포인터를 통해 구조체 멤버를 바꾸지 않겠다는 뜻이지, 함수가 GPIO 하드웨어까지 변경하지 않는다는 뜻은 아니다.
배열은 포인터 변수 자체가 아니다. 배열 이름은 대부분의 식에서 첫 원소를 가리키는 포인터로 변환되지만 sizeof 배열에는 배열 전체 크기가 적용된다. 원소 접근 a[i]는 유효 범위 안에서 *(a+i)와 연결해 이해한다.
## 3. 소프트웨어 계층을 나누는 이유
Application은 “언제 증가하고 언제 멈출까”를 결정한다. Driver는 “이 FND에 어떤 핀 패턴을 보낼까”를 처리한다. HAL은 MCU 주변장치 제어를 제공하고, CMSIS 장치 정의는 레지스터 주소와 구조를 표현한다.
헤더(.h)에는 호출 방법인 선언을, 소스(.c)에는 실제 함수 정의를 둔다. 헤더를 포함했다고 다른 .c가 자동으로 빌드되는 것은 아니므로 프로젝트 빌드 대상도 확인한다. 선언과 정의의 반환형·매개변수는 일치해야 한다.
여기서 software stack은 “소프트웨어 계층”이라는 말이며, 지역 변수·복귀 정보와 관련된 메모리 stack과는 다른 의미다.
## 4. HAL_GetTick()으로 시간을 나누기
정확한 함수 이름은 HAL_GetTick()이다. 기본 HAL 시간 기준에서는 SysTick이 HAL_IncTick()을 호출해 tick을 갱신한다. HAL_GetTick()을 자주 읽는다고 시간이 더 빠르게 증가하지는 않는다.
```c
/* 초기화 후 한 번 실행 */
uint32_t previous = HAL_GetTick();

/* 아래 코드는 main 반복문 안에서 실행 */
uint32_t now = HAL_GetTick();
if ((uint32_t)(now - previous) >= 100)
{
    previous = now;
    /* 카운터를 한 번 증가 */
}
/* 자리 스캔과 버튼 확인을 계속 실행 */
```
이 예제는 최소 100 ms 간격의 처리이며, 루프가 오래 지연되면 모든 누락 횟수를 자동 보상하지 않는다. unsigned 뺄셈을 이용한 경과 시간 비교는 tick의 한 바퀴를 넘겨 방치하지 않는 등 적용 조건에서 래핑을 다룰 수 있다. “unsigned면 모든 overflow 문제가 해결된다”는 뜻은 아니다. 이 설명을 위해 기존 프로젝트 자료형을 바꿀 필요는 없다.
## 5. 버튼 상태, 엣지, 디바운싱
상태는 “지금 누르고 있는가”, 엣지는 “방금 뗌에서 누름으로 바뀌었는가”다. 풀업 버튼이면 HIGH→LOW가 누름 엣지다.
기계식 버튼은 한 번 눌러도 잠시 여러 번 흔들릴 수 있다. 엣지 검출만으로 이 바운스를 제거할 수는 없다. 입력이 일정 시간 유지됐는지 확인하는 디바운싱과, 안정화한 상태 변화에서 이벤트를 만드는 처리를 구분한다.
ACT_PUSH는 보통 눌리는 순간 한 번 발생한다. 다음 루프의 NO_ACT를 “버튼을 뗐다”로 해석해 LED를 끄면 잠깐 켜졌다가 꺼진다. 누르는 동안 유지하려면 ACT_RELEASED에서 끄거나 안정화된 현재 상태를 사용한다.
## 6. 실제 버튼 문제를 해결한 과정
수업 기록의 PC0 문제는 프로그램이 실행되고 버튼 검사까지 도달했지만, GPIOC->IDR의 bit 0이 누름·뗌 모두 0이었다. 따라서 먼저 상태 머신보다 입력 신호와 배선을 의심할 근거가 있었다.
```c
(GPIOC->IDR & 1)
```
이 식은 다른 비트를 가리고 bit 0만 남긴다. 이때 &는 주소 연산자가 아니라 두 피연산자 사이의 비트 AND다. &count의 단항 &와 문맥을 구분한다.
기록상 외부 저항의 연결을 GND 쪽에서 전원 쪽으로 고친 뒤 정상 동작했다. 핵심은 코드가 누름=LOW를 가정할 때 실제 입력도 뗌=HIGH, 누름=LOW가 되도록 회로가 맞아야 한다는 것이다.
**점검 순서:** 실행·다운로드 확인 → 실제 사용 핀 확인 → IDR 변화 확인 → GPIO 모드·풀업 확인 → 배선 확인 → 디바운싱·상태 전이 확인.
